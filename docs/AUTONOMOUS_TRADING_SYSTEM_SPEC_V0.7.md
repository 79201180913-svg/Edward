# Edward — Системная спецификация автономной торговли v0.7

**Версия:** 0.7  
**Статус:** зафиксировано для `main`  
**Назначение:** описывает фактическую системную модель автономной торговли Edward v0.7: расчёт капитала и бюджета, перераспределение портфеля, построение execution plan, preflight, исполнение через брокерский контур, verification, защиту позиций и цикл автономного replanning.

---

## 1. Назначение

Автономная торговля должна реализовывать торговые решения Edward без ручного подтверждения каждой операции при сохранении контроля капитала, количества позиций, актуальности состояния счёта, последовательности операций и защитных ордеров.

Основной принцип v0.7:

> один торговый шаг → фактическое исполнение → проверка результата → обновление состояния → новое планирование.

Автоторговля не должна безусловно исполнять заранее сформированный многошаговый план, если состояние счёта после предыдущей операции изменилось.

---

## 2. Основные принципы

### 2.1. Бюджет определяется фактическим счётом

Абсолютный бюджет в алгоритме не задаётся. Бюджет рассчитывается из актуального состояния счёта.

Источники:

- `portfolio_value` — стоимость портфеля;
- `cash` — денежные средства;
- `blocked` — заблокированные средства;
- `securities` — стоимость ценных бумаг;
- `reserve_pct` — процент резерва;
- `slots` — допустимое число позиций.

Нельзя использовать захардкоженный инвестиционный бюджет вроде `50000` или `100000` как источник расчёта стратегии.

### 2.2. Состояние счёта является источником истины

Перед автономным исполнением используется актуальное состояние счёта. После исполнения состояние обновляется повторно.

### 2.3. Планирование и исполнение разделены

Анализ и allocation формируют решения. Execution plan превращает решения в упорядоченные шаги. Только execution-контур отправляет заявки брокеру.

### 2.4. Проверка перед исполнением обязательна

Даже ранее сформированный план должен проходить актуальный preflight.

### 2.5. Сделка подтверждается фактом, а не только ответом submit

Принятие заявки брокером не равно подтверждённому изменению позиции. После терминального исполнения выполняется verification по свежему состоянию счёта.

### 2.6. После успешного шага план строится заново

Следующее решение должно учитывать изменившиеся cash, позиции, слоты, заявки и результаты анализа.

---

## 3. Модель капитала

`BudgetPlanningService` строит `BudgetPlan` из `FinancialSummary` и `BudgetPlanningPolicy`.

### 3.1. Расчёт резерва

`reserve = portfolio_value × reserve_pct / 100`

### 3.2. Плановый бюджет

`planning_budget = max(0, portfolio_value - reserve)`

### 3.3. Инвестируемый cash

`investable_cash = max(0, cash - reserve)`

Стоимость уже имеющихся ценных бумаг не превращается автоматически в доступный cash.

### 3.4. Целевой размер позиции

`target_position_value = floor(planning_budget / slots)` с денежным округлением до `0.01`.

Если целевой размер позиции меньше `min_position_value`, целевой размер становится `0`.

### 3.5. Валюта

В `BudgetPlan` сохраняется валюта финансового состояния; по умолчанию используется `RUB`.

---

## 4. Ограничение количества позиций

`slots` задаёт максимальное число одновременно удерживаемых позиций.

Система должна учитывать:

- уже занятые позиции;
- позиции, которые будут закрыты;
- новые позиции;
- операции замены;
- итоговое количество позиций после моделирования плана.

Если итоговое количество позиций превышает `slots`, preflight отклоняет план с причиной `SLOT_LIMIT_EXCEEDED`.

---

## 5. Входные данные планирования

Автоторговый контур использует:

### 5.1. Состояние счёта

- капитал;
- cash;
- blocked cash;
- текущие позиции;
- активные заявки;
- валюта.

### 5.2. Рыночные возможности

Для каждого кандидата используются, как минимум:

- `ticker`;
- `instrument_uid`;
- `decision`;
- `opportunity_score`;
- `risk_score`;
- `recommended_value` при наличии.

### 5.3. Анализ текущего портфеля

Для каждой существующей позиции используются решение, score, risk и рекомендуемое действие.

---

## 6. Действия портфеля

Поддерживаемые allocation actions:

| Action | Назначение |
|---|---|
| `BUY` | открыть новую позицию |
| `ADD` | увеличить существующую позицию |
| `HOLD` | сохранить позицию |
| `REDUCE` | уменьшить позицию |
| `SELL` | полностью закрыть позицию |
| `REPLACE` | заменить существующую позицию новой |

---

## 7. Выбор новых позиций

Для открытия новых позиций рассматриваются кандидаты с решением `BUY`.

Кандидаты сортируются по opportunity score и риску. При наличии свободных слотов выбираются наиболее привлекательные кандидаты при соблюдении:

- отсутствия этой позиции в текущем портфеле;
- отсутствия дубликата среди выбранных кандидатов;
- наличия свободного слота;
- положительного `target_position_value`;
- наличия `investable_cash`.

Стоимость новой позиции ограничивается минимумом из целевой стоимости позиции и оставшегося доступного cash.

---

## 8. Перераспределение портфеля

Если все слоты заняты, система может заменить существующую позицию на более привлекательную.

Замена допускается при выполнении политики `ReallocationPolicy`:

- score нового кандидата должен превышать score заменяемой позиции не менее чем на `replacement_score_delta`;
- риск нового кандидата не должен превышать риск заменяемой позиции более чем на `max_replacement_risk_increase`.

В текущей политике значения по умолчанию:

- `replacement_score_delta = 5.0`;
- `max_replacement_risk_increase = 0.0`.

Цель замены — не увеличить число позиций, а улучшить состав портфеля в рамках существующего лимита слотов.

---

## 9. Правило REPLACE

`REPLACE` преобразуется в два последовательных execution steps:

1. `SELL` исходной позиции;
2. `BUY` новой позиции.

Новый BUY получает `depends_on = sequence` шага SELL.

Следовательно, новая позиция не может быть открыта до подтверждённого завершения освобождающей операции.

---

## 10. Execution Plan

`AutonomousExecutionPlanService` преобразует allocation actions в `AutonomousExecutionPlan`.

Каждый `ExecutionPlanStep` содержит:

- `sequence`;
- `action`;
- `ticker`;
- `instrument_uid`;
- `target_value`;
- `source_ticker`;
- `source_instrument_uid`;
- `depends_on`;
- `requires_revalidation`;
- `execution_ready`;
- `reason`.

Execution plan не отправляет заявки самостоятельно.

## 11. Автономный цикл

Полный цикл:

```text
START
  ↓
Проверка режима AUTONOMOUS
  ↓
Проверка, что автоторговля включена
  ↓
Refresh account state
  ↓
Расчёт BudgetPlan
  ↓
Анализ рынка и текущего портфеля
  ↓
Portfolio Reallocation
  ↓
Build Execution Plan
  ↓
Protection Reconciliation
  ↓
Preflight
  ↓
Выбор первого шага
  ↓
Submit
  ↓
Ожидание терминального состояния
  ↓
Refresh account state
  ↓
Verification
  ↓
Protection для BUY/ADD
  ↓
Шаг завершён
  ↓
Новое планирование
  ↓
Есть действия?
  ├─ Да → повторить
  └─ Нет → COMPLETE
```

`AutonomousReplanningCycleService` после каждого подтверждённого шага сохраняет обновлённое состояние и строит новый план.

---

## 12. Режим исполнения

Для автономного исполнения требуется `ExecutionMode.AUTONOMOUS`.

Если выбран другой режим:

`AUTONOMOUS_MODE_REQUIRED`

Если автономная торговля выключена:

`AUTONOMOUS_TRADING_DISABLED`

Контроллер хранит состояние `enabled` и предоставляет операции включения/выключения.

---

## 13. Preflight

Preflight выполняется перед автономным исполнением и получает:

- execution plan;
- актуальный budget;
- актуальное account state.

Проверки выполняются по следующим группам.

### 13.1. Наличие плана

Пустой план отклоняется:

`EMPTY_EXECUTION_PLAN`

### 13.2. Последовательность

Sequence должен иметь вид `1, 2, 3, ...`.

Ошибка:

`INVALID_SEQUENCE`

### 13.3. Dependencies

`depends_on` должен ссылаться на существующий предыдущий шаг.

Ошибка:

`INVALID_DEPENDENCY`

### 13.4. Проверка позиций

- `SELL` требует существующей позиции;
- `BUY` запрещён для уже удерживаемого инструмента;
- `ADD` требует существующей позиции;
- `REDUCE` работает с существующей позицией;
- неизвестное действие отклоняется.

Возможные причины:

- `POSITION_NOT_FOUND`;
- `BUY_ALREADY_HELD`;
- `ADD_POSITION_NOT_FOUND`;
- `UNSUPPORTED_PLAN_ACTION`.

### 13.5. Проверка конфликтующих заявок

Активные заявки по инструменту блокируют создание конфликтующей операции.

Учитываются статусы:

- `NEW`;
- `PENDING`;
- `WAITING_CONFIRMATION`;
- `EXECUTING`;
- `SUBMITTED`;
- `PARTIALLY_FILLED`.

Ошибка:

`ACTIVE_ORDER_CONFLICT`.

### 13.6. Проверка cash

Для BUY/ADD рассчитывается требуемая стоимость.

Для SELL учитывается потенциально освобождаемая стоимость.

Если:

`buy_value > investable_cash + released_value`

план отклоняется с `INSUFFICIENT_INVESTABLE_CASH`.

### 13.7. Проверка slots

Моделируется итоговый набор позиций. При превышении лимита:

`SLOT_LIMIT_EXCEEDED`.

---

## 14. Protection Reconciliation

До начала автономного исполнения контролируется соответствие открытых long-позиций и активных защитных Stop Loss.

Для каждой позиции с положительным количеством проверяется:

1. наличие активного Stop Loss;
2. соответствие инструмента;
3. соответствие количества.

Ошибки:

- `PROTECTION_REQUIRED:<uid>` — защита отсутствует;
- `PROTECTION_MISMATCH:<uid>:position=...:stop=...` — количество защиты не соответствует позиции;
- `ORPHAN_PROTECTION:<uid>` — существует защита для отсутствующей позиции.

При проблеме результат reconciliation становится `RECONCILIATION_ERROR`.

---

## 15. Поведение при нарушении protection

Контроллер не должен продолжать автономную торговлю при неподтверждённом состоянии защиты.

Если reconciliation не пройдена:

1. при наличии recovery-контуров выполняется попытка восстановления;
2. выполняется повторная reconciliation;
3. если защита всё ещё не подтверждена, автономное исполнение блокируется.

Причины:

- `PROTECTION_RECONCILIATION_FAILED`;
- `PROTECTION_RECOVERY_FAILED`.

---

## 16. Исполнение через брокерский контур

Для `AUTONOMOUS` используется автономная отправка через `ExecutionBridgeService`.

После submit допустимы промежуточные состояния:

- `SUBMITTED`;
- `PARTIALLY_FILLED`;
- `FILLED`;
- `RECONCILED`.

Если заявка остаётся в `SUBMITTED` или `PARTIALLY_FILLED`, система ожидает терминального состояния.

Текущие параметры execution sequence:

- timeout: 30 секунд;
- poll interval: 1 секунда.

---

## 17. Условия успешного исполнения

Шаг может перейти к verification только после терминального состояния `FILLED` или `RECONCILED`.

Другие состояния считаются ошибкой исполнения.

---

## 18. Verification

После терминального исполнения система снова обновляет состояние счёта.

Verification сопоставляет:

- состояние позиции до операции;
- фактически исполненное количество;
- состояние позиции после операции.

### BUY / ADD

Требуемое итоговое количество:

`before_quantity + executed_quantity`

Фактическое количество должно быть не меньше требуемого.

Ошибка:

`POSITION_QUANTITY_NOT_REACHED`.

### SELL

После полного закрытия:

`actual_quantity == 0`

Иначе:

`POSITION_NOT_CLOSED`.

### REDUCE

Фактическое количество должно уменьшиться на требуемую величину.

Ошибка:

`POSITION_NOT_REDUCED_ENOUGH`.

---

## 19. Защита новой позиции

Для `BUY` и `ADD` после успешного verification выполняется создание защитного Stop Loss на фактически исполненное количество.

Последовательность:

```text
BUY / ADD
  ↓
FILLED / RECONCILED
  ↓
VERIFY
  ↓
CREATE STOP LOSS
  ↓
PROTECTED
  ↓
COMPLETED
```

Если защита не создана или сервис защиты вернул ошибку, шаг не считается успешно завершённым.

---

## 20. Состояния execution step

Фазы:

- `PREPARING` — подготовка и получение актуального состояния;
- `EXECUTING` — отправка и ожидание брокера;
- `VERIFYING` — проверка фактического результата;
- `PROTECTED` — создана/подтверждена защита;
- `COMPLETED` — шаг успешно завершён;
- `FAILED` — цикл завершён с ошибкой;
- `STOPPED` — исполнение остановлено.

Для каждого шага могут формироваться phase events с sequence, phase и message.

---

## 21. Execution Events и UI

Автономный контур должен публиковать события исполнения для наблюдаемости.

Основные статусы событий:

- `PLAN`;
- `SUBMITTING`;
- `SUBMITTED`;
- `VERIFYING`;
- `EXECUTED`;
- `FAILED`.

Событие может содержать:

- iteration;
- sequence;
- action;
- ticker;
- instrument UID;
- target value;
- execution ID;
- broker status;
- reason.

UI должен показывать пользователю текущее состояние автономного исполнения, execution ID, статус и причину остановки/ошибки.

---

## 22. Ошибки и fail-safe поведение

Критические ошибки должны останавливать текущий автономный цикл, а не заставлять систему продолжать работу на предположительно устаревших данных.

Критические категории:

- ошибка refresh состояния счёта;
- rejection preflight;
- ошибка submit/исполнения;
- timeout/непереход в терминальное состояние;
- ошибка verification;
- ошибка protection;
- ошибка protection reconciliation;
- достижение лимита итераций.

---

## 23. Replanning

`AutonomousReplanningCycleService` работает итерационно.

На каждой итерации:

1. используется актуальное состояние;
2. строится новый execution plan;
3. выбирается первый исполняемый шаг;
4. шаг выполняется;
5. состояние обновляется;
6. результат проверяется;
7. при успехе новый план строится уже от обновлённого состояния.

Если план пуст:

`COMPLETED`

Если возникла ошибка исполнения или verification:

`EXECUTION_ERROR:...` или `VERIFICATION_ERROR:...`

Если достигнут лимит:

`MAX_ITERATIONS_REACHED`.

Текущий максимальный лимит по умолчанию — `50` итераций.

---

## 24. Правило остановки

Автоторговля прекращает текущий цикл, если:

- режим не `AUTONOMOUS`;
- автоторговля отключена;
- план пуст — в этом случае цикл считается успешно завершённым;
- preflight отклоняет операцию;
- состояние счёта невозможно актуализировать;
- брокер не подтвердил терминальное исполнение;
- verification не подтверждает фактический результат;
- protection не обеспечена;
- превышен `max_iterations`.

## 25. Инварианты системы

### INV-01 — Live Capital

Бюджет всегда выводится из фактического состояния счёта.

### INV-02 — No Hardcoded Budget

Абсолютный торговый бюджет не является параметром стратегии.

### INV-03 — Slot Limit

Количество одновременно удерживаемых позиций не должно превышать `slots`.

### INV-04 — Fresh State

Перед автономным шагом используется актуальное состояние счёта.

### INV-05 — Preflight

Каждый автономный шаг проходит preflight перед submit.

### INV-06 — Verification

Факт исполнения подтверждается по обновлённому состоянию счёта.

### INV-07 — Protection

Новая long-позиция должна быть защищена после успешного исполнения.

### INV-08 — Replanning

После успешного шага дальнейшие действия определяются новым планом.

### INV-09 — Dependencies

Зависимый шаг не выполняется до успешного завершения зависимости.

### INV-10 — Fail Safe

При критической неопределённости система останавливает автономное исполнение.

## 28. Вне границ v0.7

Следующие изменения не должны вноситься как скрытые исправления v0.7:

- изменение формулы opportunity score;
- изменение формулы risk score;
- изменение стратегии анализа рынка;
- изменение базового принципа динамического бюджета;
- изменение правил замены позиций;
- изменение поведения при orphan protection.

Изменение бизнес-логики требует отдельного hotfix или новой версии спецификации.

## 29. Эталонный сценарий

Пример для счёта с небольшим капиталом:

```text
1. Получить live portfolio state.
2. Рассчитать capital, reserve, cash и slots.
3. Рассчитать target position value.
4. Проанализировать текущие позиции.
5. Проанализировать рынок.
6. Определить BUY / HOLD / ADD / REDUCE / SELL / REPLACE.
7. Построить execution plan.
8. Проверить protection текущего портфеля.
9. Выполнить preflight.
10. Взять первый шаг.
11. Отправить заявку.
12. Дождаться FILLED / RECONCILED.
13. Обновить account state.
14. Проверить фактическое количество.
15. При BUY/ADD создать Stop Loss.
16. Считать шаг завершённым.
17. Заново проанализировать состояние.
18. Построить новый план.
19. Повторять до отсутствия действий или критической остановки.
```

## 30. Итоговая модель

Edward v0.7 — это не механизм пакетной отправки заранее рассчитанных заявок. Это замкнутый автономный контур принятия и исполнения решений:

> **Analyze → Budget → Allocate → Plan → Preflight → Execute → Verify → Protect → Refresh → Replan.**

Главным источником истины для исполнения является фактическое состояние торгового счёта, а не первоначальный план.
